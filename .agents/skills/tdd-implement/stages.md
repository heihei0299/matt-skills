# 阶段详细定义

## 阶段 ①：理解需求

### 入口条件
- 用户提供了 spec 或一组 ticket

### 操作
1. 完整读取 spec/ticket 内容
2. 若存在 `CONTEXT.md` 和 `docs/adr/`，先阅读，确保术语和 ADR 决策不被违背
3. 如有歧义，先向用户澄清再继续

### 出口条件
- 能用自己的话复述需求
- 无未澄清的歧义

### 边界规则
- 不得在需求未澄清时跳过本阶段
- 不在此阶段做任何实现或测试设计

---

## 阶段 ②：确认 Seams（测试接缝）

### 入口条件
- 需求已澄清，无歧义

### 操作
1. 列出所有将要测试的公共接口（seams）
2. 每个 seam 需包含：名称、输入、预期输出
3. 向用户展示 seams 清单并确认
4. 在用户确认之前，不得写任何测试代码

### 出口条件
- 用户明确同意了 seams 清单

### 边界规则
- 一个 seam 对应一个公共接口，不是内部函数
- Seams 覆盖关键路径和复杂逻辑，不必覆盖所有边缘情况
- 用户确认后才进入下一阶段

> Seams 定义参考：[tdd 技能](../tdd/SKILL.md#seams--where-tests-go)

---

## 阶段 ③：TDD 开发循环

### 入口条件
- Seams 已确认

### 操作

严格遵循 tdd 技能的全部规定（参见 [tdd/SKILL.md](../tdd/SKILL.md)），按垂直切片方式逐 seam 推进。

#### 3a. 红（Red）
1. 为当前 seam 写一个会失败的测试
2. 测试必须通过公共接口验证行为，不得耦合实现细节
3. 不得提前为后续 seam 写测试（禁止水平切片）
4. 断言值必须来自独立来源（字面量、手算例子），不得用代码同源计算

#### 3b. 绿（Green）
1. 只写刚好能让当前测试通过的最小代码
2. 不得添加未被测试覆盖的功能
3. 不得在此阶段重构

#### 3c. 切换 seam
1. 当前 seam 的红-绿完成后，进入下一个 seam
2. 每次只做一个 seam → 一个测试 → 一个实现

#### 3d. Typecheck
- 每个 cycle 结束后运行 typecheck
- 发现问题立即修复，修复后再继续

### 出口条件
- 所有 seams 的红-绿循环完成
- Typecheck 通过

### 边界规则
- 不得水平切片
- 不得超前实现
- 不得在循环阶段重构
- 不得跳过 typecheck

> Mock 指南：[tdd/mocking.md](../tdd/mocking.md)
> 好测试标准：[tdd/tests.md](../tdd/tests.md)

---

## 阶段 ④：完整测试套件

### 入口条件
- 阶段 ③ 完成，typecheck 通过

### 操作
1. 运行仓库的完整测试套件
2. 检查所有测试是否通过

### 出口条件
- 全部测试通过

### 回退
- 若有测试失败 → 回到阶段 ③，修复后重新运行

### 边界规则
- 不得跳过本阶段直接进入 Code Review
- 修复测试后必须重新运行完整套件确认

---

## 阶段 ⑤：Code Review

### 入口条件
- 完整测试套件通过

### 操作
1. 调用 `/code-review` skill 审查当前所有改动
2. 根据审查结果判断：

### 出口条件
- Code review 通过

### 回退路由
| 发现问题类型 | 回退目标 |
|-------------|----------|
| 实现错误 | 回退到 ③，修复实现 |
| Seams 遗漏 | 回退到 ②，补充 seams |
| 需求偏差 | 回退到 ①，澄清需求 |

### 边界规则
- 不得在 code review 未通过时进入 commit
- 重构在此阶段进行，而非 TDD 循环阶段

---

## 阶段 ⑥：Commit

### 入口条件
- Code review 通过

### 操作
1. 将工作提交到当前分支
2. 附带清晰的 commit message

### 出口条件
- Commit 完成

### 边界规则
- 不得在 code review 之前 commit
- Commit message 应描述变更内容而非过程
